## 9. 生产容器与 HTTPS 复测

本地生产演练使用独立空数据库、自签 TLS 证书和独立生产容器，不读写日常开发库。生产配置门禁另使用符合真实协议约束的隔离配置验证，8 项必需设置、不同认证密钥、数据库 `sslmode=verify-full` 和 `rediss://` 均通过。

- 当前源码顺序构建 API、Worker、Gateway 和 Migrate 四个目标成功；Compose 并行构建曾遇到一次 Docker Desktop BuildKit gRPC 会话错误，改用逐目标构建后全部成功。
- 全新数据库由 Migrate 镜像一次应用 41 个迁移成功，API 不在启动时自行迁移。
- API、Worker、Gateway 均为 `healthy`，且重启策略为 `unless-stopped`。
- API 端口只存在于 Docker 内网，宿主机发布端口为空；外部只开放 HTTP/HTTPS 网关。
- HTTPS 主页、`/healthz`、`/api/health` 均为 `200`，HTTP 返回 `301`；TLS 1.2、1.3 成功，TLS 1.0 被拒绝。
- 瞬时向快速 API 路径发送 1,000 个管线请求：650 个到达 API，350 个由网关返回 `429`；限流窗口后健康接口立即恢复 `200`。
- 受控重建 API 后容器 ID 和启动时间均变化，API、Worker 和网关代理恢复健康。
- 使用 Git `7d99369` 重建上一版网关并切换回滚标签，健康检查通过；随后重新发布当前修复版并再次通过。
- 当前修复版主页标题为“妆序｜化妆部预约系统”，适用于五类统一网页角色。
- 生产容器近 15 分钟日志未发现 `ERROR`、`FATAL`、未处理拒绝或连接异常。

复测发现并修复一项真实网关缺陷：Nginx 的 `location /` 与 `location /assets/` 设置自己的缓存响应头后，不再继承服务器级安全头，导致主页和静态资源缺少 HSTS、`X-Frame-Options` 等。安全头现集中在 `deploy/security-headers.conf`，服务器、主页和静态资源位置显式复用；容器内 `nginx -t`、主页和静态 JS 实际响应均验证通过。

当前执行环境禁止从容器内部强制杀死 PID 1，因此没有绕过限制制造进程崩溃。已验证 `unless-stopped` 声明和受控重建恢复；“真实进程异常退出后由 Docker 自动拉起”仍需在预发布主机执行一次。正式托管 PostgreSQL、Redis 的 TLS 握手及正式证书链也只能在目标资源确定后验收。
