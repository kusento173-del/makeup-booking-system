## 7. 全网页端容量复测

测试使用隔离数据库 `makeup_booking_perf_20260726`，已升级至当前 41 个迁移。数据规模为 3 个场地、10,000 名主播、200 名化妆师、209 名运营、约 54.9 万条预约，未读写日常开发数据库。

- 100 路真实 HTTP 请求同时抢同一化妆师同一档期：1 次创建成功、99 次返回 `409 Conflict`，无 `500`；成功预约随后已取消清理。
- 600 个并发虚拟用户持续随机查询三场地大体量排班看板和次日可预约档期。
- 实际持续时间：902.992 秒。
- 请求总数：239,017。
- 失败请求：0；全部为 `200`。
- 平均吞吐：264.69 请求/秒。
- 排班看板 p95：11.64 毫秒。
- 可预约档期 p95：13.78 毫秒。
- 响应正文累计读取约 2.93 GB，避免只测连接建立而未消费实际响应。
- 访问令牌在第 7 分钟和第 14 分钟续签，负载与会话均未中断。
- 测试结束后数据库检查：化妆师时间重叠 0、主播时间重叠 0、主播单日超过两次 0、同一固定规则同日重复预约 0。

仓库新增可重复执行的 `pnpm test:capacity`。默认参数即 600 并发、15 分钟；可通过 `CAPACITY_CONCURRENCY`、`CAPACITY_DURATION_SECONDS` 和 `CAPACITY_DATABASE_NAME` 在隔离环境调整。脚本会自动选择空闲本地端口，执行迁移、启动独立 API、建立临时测试会话并在结束后撤销，不依赖人工登录状态。

运行期间 Node PostgreSQL 驱动输出一条上游弃用警告：并发请求下检测到同一客户端已有查询时再次调用 `query()`。本次没有造成失败、超时或数据不一致，但在未来升级至 `pg@9` 前需要继续跟踪 Prisma PostgreSQL adapter 的兼容性。

Redis 故障使用独立 API 进程和临时管理员会话验证：

- Redis 正常时，健康检查和受保护排班查询均为 `200`。
- 停止 Redis 后，API 进程未退出；健康检查返回 `500`，使网关可停止向异常实例分流。
- 已持有有效访问令牌的排班查询仍返回 `200`，数据库核心只读功能保持可用。
- 依赖 Redis 限流的会话刷新返回 `503`，没有绕过限流降级为不安全登录。
- Redis 恢复后未重启 API，健康检查和会话刷新自动恢复为 `200`。
- 测试结束后 PostgreSQL 与 Redis 容器均为 `healthy`，临时会话已撤销。

仓库新增 `pnpm test:redis-recovery`，脚本会在 `finally` 清理阶段保证 Redis 被重新拉起并等待健康，避免失败测试把本地基础设施留在中断状态。
