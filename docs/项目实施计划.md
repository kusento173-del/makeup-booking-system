# 化妆部预约系统项目实施计划

> 文档版本：V1.2
> 编制日期：2026-07-27
> 当前阶段：M10 全网页端迁移已完成；进入生产准备与真实业务验收
> 实施范围：第一阶段 P0，从原型确认到试运行和正式上线

> **计划修订：** M8 的小程序交付物已经由响应式手机网页替代；Taro、微信登录、绑定码和小程序发布步骤已取消。旧里程碑文字保留用于追溯，不再作为待办，当前进度以[当前迭代](当前迭代.md)为准。

---

## 1. 文档目的

本文档确定项目按什么顺序开发、每个阶段交付什么、依赖什么、如何验收，以及何时可以进入下一阶段。

实施原则：

1. 先确认业务和交互，再冻结接口和数据库。
2. 先实现主数据、权限和时间规则，再实现预约。
3. 并发、事务、审计和自动化测试与功能同时建设，不能上线前临时补。
4. 先完成可工作的模块化单体，不提前拆微服务。
5. 每个阶段只引入必要代码和依赖，保持结构精简、边界清晰、易测试和易维护。
6. 每个完整变更通过对应检查后创建一次 Git 提交。
7. 人员 Excel、密钥、生产数据和数据库备份永远不进入 Git。

---

## 2. 项目目标

第一阶段完成后：

- 主播可以在手机端预约、改期、取消、查看排班和请假。
- 运营可以管理负责主播的普通预约和固定申请。
- 化妆师可以设置班次、查看排班、请假和申请加班。
- 客服可以管理本场地排班、代录、审批、维护人员和导出。
- 管理员可以管理全场地主档、关系、账号、导入、配置和审计。
- 系统自动防止重叠、重复、越权、跨场地和每日第三次预约。
- 系统自动生成固定预约，并由各角色在网页内查看最新排班。
- 系统排班可以替代当前需要清洗的手工表。

## 3. 第一阶段范围边界

### 3.1 必须交付

- 五类角色与场地权限。
- 人员主档及主播—运营关系。
- 化妆师班次、工作日、加班和请假。
- 普通预约及每日两次限制。
- 改期、换人、修改妆容类型和取消。
- 固定新建、变更和取消审批。
- 固定预约滚动生成。
- 排班查询和 Excel 导出。
- 自动完成、后台任务重试和失败跟踪。
- 导入、审计、监控、备份和恢复。
- 手机端与 Web 后台。

### 3.2 不在第一阶段

- 绩效和奖金计算。
- 直播间预约。
- 讲师角色。
- 未到场状态。
- 第三次预约特批。
- 自动推荐或自动分配化妆师。
- 现有固定主播名单导入。
- 复杂经营分析。

发现边界外需求时先记录到后续清单，不直接混入当前开发阶段。

## 4. 开工前决策门

### 4.1 当前技术基线

- 五类角色统一采用 React 响应式网页，不再建设微信小程序。
- 主播、运营和化妆师使用手机优先布局，客服与管理员使用电脑优先布局。
- 全部角色使用全局唯一登录名和密码；首次使用临时密码登录后必须改密。
- 后端使用 NestJS 模块化单体。
- PostgreSQL 是预约事实和冲突约束的最终来源。
- Redis 为缓存、限流和队列扩展提供基础；Worker 处理定时维护和导出任务。
- 所有日期边界按 Asia/Shanghai。
- 历史固定主播名单不导入。
- 无法匹配的主播—运营关系按未分配处理。

### 4.2 对应模块开发前必须确认

| 决策 | 最晚确认阶段 | 暂定基线 |
|---|---|---|
| 手机端最终形态 | M10 迁移开始前 | 已确认：与电脑端共用 React 响应式网页 |
| 账号首次开通方式 | M10 身份改造前 | 已确认：管理员或本场地客服创建账号并签发临时密码 |
| 外部通知 | 第一阶段不建设 | 已确认 |
| 加班待审核是否过期 | 加班模块验收前 | 暂不自动过期 |
| Excel 默认分场地或合并 | 导出模块验收前 | 客服分场地、管理员支持合并 |
| 生产云、域名和备案主体 | 部署环境准备前 | 待选择 |

未确认项不能用多套正式实现“同时兼容”。只保留清晰接口边界，在决策后实现一种方案。

## 6. 工期估算方法

在团队人员尚未确定时，不承诺具体上线日期。使用以下基线估算：

| 工作量 | 含义 |
|---|---|
| S | 约 1 至 2 个有效开发日，低依赖 |
| M | 约 3 至 5 个有效开发日，中等业务复杂度 |
| L | 约 6 至 10 个有效开发日，跨模块或高风险 |
| XL | 需要拆分为多个任务，不能作为单个开发任务 |

“有效开发日”包含代码、自动化测试、评审和文档更新，不等同于自然日。微信资质、域名备案、业务确认、测试等待和整改时间另算。

若由一名全栈开发者主导，产品和业务人员按时评审，第一阶段开发、验证和单场地试运行通常需要约 14 至 18 周。若前端、后端、测试可以并行，通常可压缩到约 9 至 12 周。该数字只用于资源规划，必须在 M0 完成后按任务清单重新估算。

### 7.2 交付物

- 普通预约、第二次预约、改期、固定、请假、审批和排班导出原型均可走通。

- 业务负责人确认可以进入工程开发。

## 8. M1：工程与环境基线

### 8.1 工程初始化

建立 pnpm workspace：

- apps/api：NestJS API。
- apps/worker：BullMQ Worker。
- apps/admin-web：客服与管理员后台。
- apps/miniapp：主播、运营和化妆师小程序。
- packages/shared-types：稳定的共享类型和枚举。
- packages/api-client：由 OpenAPI 生成的客户端。
- packages/validation：确有跨端复用价值的输入结构校验。
- packages/config：统一 ESLint、TypeScript 等工程配置。
- prisma：模型和迁移。
- tests：端到端和性能测试。

共享包只放稳定、真正复用的内容。业务规则仍由后端领域模块统一实现，不能把前端展示逻辑包装成“共享规则”后成为第二事实来源。

### 8.2 基础工具

- Node.js LTS 和 pnpm 锁定。
- TypeScript 严格模式。
- ESLint、Prettier、Husky 和 lint-staged。
- Vitest 或 Jest。
- Playwright。
- Docker Compose：PostgreSQL、Redis 和本地依赖。
- 环境变量样例，不包含真实密钥。
- Git 提交规范。

### 8.3 CI

每次提交或合并请求执行：

1. 安装锁定依赖。
2. 类型检查。
3. 格式与 lint。
4. 单元测试。
5. 数据库迁移验证。
6. API 集成测试。
7. 核心端到端冒烟。
8. 构建四个应用。
9. 检查敏感文件和依赖漏洞。

### 8.4 退出标准

- 新开发者按照 README 能启动全部本地依赖和应用骨架。
- 空数据库可以完成全部迁移。
- CI 稳定通过。
- 示例环境变量不含真实信息。
- 首次工程提交已创建并可回退。

工作量：M。

## 9. M2：主数据、身份与权限

### 9.1 数据库基础

按数据字典实现：

- 场地。
- 账号、角色和会话。
- 主播、化妆师、运营和客服主档。
- 主播—运营有效期关系。
- 操作日志。
- 导入批次基础。

数据库迁移必须包含唯一约束、外键、有效期约束和必要索引，不把关键唯一性只留在应用层。

### 9.2 身份模块

- 微信登录适配器。
- 账号绑定。
- 多角色选择。
- 账号和角色停用。
- 会话刷新与撤销。

外部微信接口通过适配器隔离，领域层不直接依赖微信 SDK。

### 9.3 权限模块

- 默认拒绝。
- 主播本人范围。
- 运营目标日期负责范围。
- 客服场地范围。
- 管理员全场地范围。
- 多角色实际使用角色。
- 操作前后审计。

权限由服务端从数据库计算，不能相信请求传入的场地或负责关系。

### 9.4 主档后台

- 场地管理。
- 人员列表和详情。
- 主播—运营关系管理。
- 账号与角色管理。
- 重名主播安全展示。

### 9.5 退出标准

- 权限矩阵核心测试全部通过。
- 客服不能跨场地。
- 主播不能切换 ID 操作他人。
- 运营关系有效期正确。
- 主播编号和化妆师昵称唯一约束有效。
- 所有关键写操作有审计日志。

工作量：L。

## 10. M3：班次、请假与加班

### 10.1 班次领域

- 首次班次设置。
- 工作日、上班、午休和下班。
- 不可变班次版本。
- 后续修改申请。
- 影响预览。
- 客服审批和直接代改。

先实现纯函数形式的时间合法性和区间计算，再接数据库和接口。15 分钟粒度、左闭右开区间和跨午休判断必须有单元测试。

### 10.2 可工作日期

统一实现：

- 常规工作日。
- 非工作日。
- 已批准加班。
- 化妆师请假。
- 人员停用。

预约查询、固定生成、后台时间轴和审批影响预览必须调用同一领域能力。

### 10.3 请假

- 主播请假。
- 化妆师请假。
- 影响预览和二次确认。
- 批量取消事务。
- 撤销化妆师请假时恢复由该请假取消且仍有效的固定预约；取消主播请假和单次预约不自动恢复。

此阶段先完成领域和 API；预约尚未完整时用集成测试数据验证批量取消接口，M4 后补完整端到端。

### 10.4 加班

- 化妆师申请。
- 客服审批。
- 客服或管理员直接添加已批准加班。
- 非工作日指定日期开放。

### 10.5 退出标准

- 未设置班次化妆师不可预约。
- 可工作日期和时间区间计算测试通过。
- 非工作日无排班，加班批准后可开放。
- 班次修改最早次日生效且当天不受影响。
- 请假、班次和加班权限正确。
- 审批状态并发安全。

工作量：L。

## 11. M4：普通预约闭环

### 11.1 可预约时间查询

输入：

- 主播。
- 日期。
- 时长。
- 可选化妆师。

输出只包含合法化妆师和完整时长可容纳的开始时间。查询可以使用优化和缓存，但提交时必须重新计算并由数据库约束兜底。

### 11.2 创建预约

按固定顺序实现：

1. 幂等。
2. 登录、角色和数据范围。
3. 明日起未来七日及零点锁定。
4. 主播、化妆师和同场地。
5. 资格和班次。
6. 请假。
7. 固定长期格。
8. 每日次数。
9. 主播和化妆师时间冲突。
10. 数据库写入和审计；只有导出等异步任务写外盒。

PostgreSQL 排斥约束负责同一主播和同一化妆师重叠区间的最终保护。

### 11.3 第二次预约

- 第一次直接创建。
- 第二次返回强确认所需摘要。
- 确认后直接创建。
- 第三次所有角色均禁止。

客户端提醒不能替代服务端和数据库事务中的每日序号校验。

### 11.4 取消和改期

- 取消释放档期和每日序号。
- 改期在同一事务中验证新档期、取消旧记录和创建新单次预约。
- 换化妆师和修改妆容类型均按改期。
- 新档期失败时原预约不变。
- 历史关联和取消原因完整。

### 11.5 手机端和后台

- 主播预约全流程。
- 运营代预约。
- 客服代录。
- 预约详情、取消和改期。
- 今日、明日和七日基本排班。

### 11.6 退出标准

- 预约相关自动化用例通过。
- 100 并发抢同一档期只有一个成功。
- 每日最多两次无法绕过。
- 改期故障注入不破坏原预约。
- 所有角色不能修改当天预约。
- 客服和运营数据范围正确。

工作量：XL，必须拆分为可预约查询、创建、次数、取消改期、手机端和后台六组任务。

## 12. M5：固定关系闭环

### 12.1 长期格模型

- 有效固定规则占用。
- 待审核申请占用。
- 15 分钟长期格排斥。
- 红、橙、绿可用性计算。
- 未来单次冲突和最早连续开始日期。

### 12.2 固定申请

- 仅当前运营提交。
- 每天或指定星期。
- 开始日期、时间、妆容类型和自动时长。
- 提交时锁定长期格。
- 撤回和驳回释放长期格。

### 12.3 审批与生成

- 本场地客服审批。
- 审批前重新校验。
- 通过后生成固定关系和不可变版本。
- 滚动生成至少覆盖预约窗口。
- 非工作日不生成。
- 已批准加班日可生成。
- 已有取消记录不由生成任务自动重建；撤销化妆师请假时只原子恢复该请假取消的有效固定预约。

### 12.4 变更和取消

- 星期、时间、妆容类型和生效日变更。
- 变更期间旧版本继续有效。
- 取消后写结束日期、取消未来实例并停止生成。
- 不实现暂停或恢复。
- 更换固定化妆师必须取消后重新申请。

### 12.5 退出标准

- 固定权限、时间矩阵和并发占位测试通过。
- 同一长期格只有一个规则或待审核申请。
- 固定生成幂等。
- 单日改期显示单次且不改变长期关系。
- 固定变更和取消保留完整历史。
- 历史固定主播名单未写入数据库。

工作量：L。

## 13. M6：排班看板、导出和管理后台

### 13.1 排班查询

- 今日。
- 明日。
- 未来七日。
- 指定历史日期或范围。
- 主播、运营、化妆师、客服和管理员各自数据范围。

查询使用预约作为唯一排班事实，不维护另一张可编辑排班表。

### 13.2 客服时间轴

- 按化妆师分行。
- 15 分钟刻度。
- 班次、午休、请假、非工作日和加班底纹。
- 固定与单次预约块。
- 详情抽屉。
- 筛选和刷新。

不实现拖拽直接改期，以免绕过标准事务和确认流程。

### 13.3 Excel 导出

- 客服本站导出。
- 管理员分场地或合并导出。
- 标准四列兼容当前使用格式。
- 扩展工作表保存编号、妆容类型、自动时长、预约来源和状态等结构化字段。
- 异步生成、下载权限和过期清理。

### 13.4 退出标准

- 各角色查询范围正确。
- 页面与 Excel 数量及字段一致。
- 实际化妆师和预约类型展示正确。
- 大单日导出在目标时间内完成。
- 公式注入防护通过。

工作量：L。

## 14. M7：后台任务与可观测性

- 小程序真机完成登录、绑定、排班和关键操作验证。
- 加载、空数据、错误、并发失效和会话失效状态均可恢复。

## 17. M10：单场地试点与并行运行

### 17.1 试点选择

### 17.2 试点步骤

1. 导入试点场地主数据。
2. 完成所有化妆师首次班次配置。
3. 培训客服、运营、化妆师和少量主播。

6. 观察排班查询、改期、请假和高峰预约。
7. 修复缺陷并再次回归。

### 17.3 试点指标

- 排班数量和关键字段核对一致。
- 无重叠有效预约。
- 无跨场地越权。
- 无每日第三次预约。

### 17.4 回退

- 暂停新预约入口。
- 保留已提交数据只读。
- 使用已验证导出恢复人工排班。
- 修复后从明确时间点重新切换。

回退不允许删除历史预约或审计。

工作量：至少连续 7 个业务日，外加问题修复时间。

## 19. 开发任务拆分规则

每个任务应当：

- 对应一个明确用户结果或技术能力。
- 能独立评审和测试。
- 不跨越过多业务模块。
- 包含数据库、后端、前端和测试中的实际影响。
- 明确不包含什么。
- 有完成标准。

不合格任务示例：“完成预约系统”。
合格任务示例：“实现主播 D+1 至 D+7 可预约时间查询，包含班次、午休、请假、固定格和已有预约扣减，并补充单元和 API 测试”。

XL 任务必须继续拆分，避免一个提交或一个分支包含无法审查的大量无关改动。

## 20. 代码架构执行要求

### 20.1 模块边界

建议后端模块：

- identity
- access-control
- sites
- people
- operator-relations
- shifts
- overtime
- leave
- appointments
- fixed-rules
- approvals
- schedules
- notifications
- imports
- exports
- audit

模块通过公开应用服务或领域接口协作，不能直接跨模块修改对方表。预约、请假和固定审批等跨模块事务由明确的应用服务编排。

### 20.2 分层

- 接口层：参数解析、认证上下文和响应映射。
- 应用层：用例编排、事务边界和权限调用。
- 领域层：规则、状态变化和计算。
- 基础设施层：数据库、队列、微信、文件和监控。

控制器不写业务判断，数据库仓储不决定角色权限，前端不成为规则最终执行层。

### 20.3 简洁性

- 不建立通用“万能审批引擎”；固定、班次和加班共享稳定状态结构，但保留清晰领域行为。
- 不建立可编辑的第二张排班事实表；排班从预约查询生成。
- 不为预计规模提前使用微服务、事件总线或多数据库。
- 不复制可预约时间算法。
- 不为少量字段创建无意义封装。
- 性能优化必须有查询计划、指标或压测依据。

## 21. Git 工作流

### 21.1 每项任务开始

1. 查看 Git 状态。
2. 确认没有覆盖用户或其他任务的未提交改动。
3. 阅读对应需求、规则、权限和数据设计。
4. 明确本次改动范围和测试。

### 21.2 提交前

1. 运行与改动匹配的类型检查、lint 和测试。
2. 查看未暂存和已暂存差异。
3. 确认没有人员 Excel、环境密钥、日志或备份。
4. 确认提交只包含一个完整逻辑变更。
5. 使用 feat、fix、docs、refactor、test 或 chore 前缀。

### 21.3 提交粒度示例

- chore: 初始化 pnpm workspace 和基础检查
- feat: 建立主播与运营有效期关系
- feat: 实现化妆师可工作日期计算
- feat: 实现预约并发排斥约束
- test: 覆盖百请求抢占同一档期
- docs: 更新固定开始日期规则

如果测试失败或功能尚未形成一致状态，不创建“完成”提交。

## 22. 完成定义

每个功能必须同时满足：

1. 产品和交互符合已确认文档。
2. 服务端权限和业务规则完整。
3. 数据库约束、事务和索引正确。
4. 正常、失败、权限、边界和并发路径有测试。
5. 页面具备加载、空、错误和数据变化状态。
6. 操作日志和业务状态一致。
7. 没有敏感数据、无关功能或过度抽象。
8. 代码职责清晰、命名准确并通过评审。
9. 自动化检查通过。
10. 相关文档已同步。
11. 已创建范围明确的 Git 提交。

“页面能用”但服务端可被绕过、并发会重复或没有测试，不算完成。

## 24. 风险清单

| 风险 | 影响 | 预防与应对 |
|---|---|---|
| 登录绑定方案迟迟未定 | 身份模块返工 | 在 M2 前冻结一种方案 |
| 人员名单持续变化 | 迁移结果过期 | 可重复预检，正式上线前做增量导入 |
| 主播—运营关系无法匹配 | 运营无权限代操作 | 明确留空，后台再分配，不模糊匹配 |
| 班次未及时设置 | 化妆师不可预约 | 工作台提醒、客服代设和上线检查 |
| 并发产生重复预约 | 排班错误 | PostgreSQL 排斥约束、事务和并发测试 |
| 规则散落在多端 | 行为不一致 | 领域服务唯一实现，前端只提示 |
| 固定生成重复或漏生成 | 排班缺失 | 唯一约束、幂等任务和补偿检查 |
| 新旧流程差异 | 业务不信任系统 | 单场地试点和连续七日逐项核对 |
| 为未来规模过度设计 | 开发慢且难维护 | 第一阶段坚持模块化单体和必要组件 |
| 真实名单误入 Git | 隐私泄露 | 忽略规则、提交检查、CI 扫描和评审 |

风险在每个里程碑结束时复核。已发生风险应转换成明确任务和负责人。

## 29. 文档结论

项目应沿着“文档与原型确认—工程基线—主数据和权限—班次—普通预约—固定—排班与后台任务—小程序业务端—迁移验证—单场地试点—全量上线”的路径推进。

这个顺序把最复杂的预约建立在可靠的身份、场地、班次和数据库约束之上，并通过自动化测试、并发验证、七日排班核对和可回退试点降低上线风险。同时坚持模块化单体、单一规则来源和小步 Git 提交，保证代码在完成全部需求的前提下保持精简、高效和易维护。
