# 化妆部预约系统角色权限矩阵

> 文档版本：V1.1｜编制日期：2026-07-27｜角色范围：主播、运营、化妆师、客服、管理员和系统任务

> **当前认证修订：** 五类角色全部通过网页账号密码登录；管理员维护全部账号，客服按场地和授权范围维护账号。本文后续“微信登录、绑定本人”和“小程序信息权限”中的渠道文字由[全网页端架构决策](全网页端架构决策.md)替代，角色动作权限和数据范围继续有效。

---

## 1. 文档目的

本文档明确每个角色可以查看什么数据、可以对谁执行什么操作，以及权限在前端、服务端和审计中的落实方式。

权限由两部分共同决定：

```text
是否允许操作 = 角色动作权限 AND 数据范围权限 AND 业务规则校验通过
```

角色有按钮不代表操作必然成功。例如管理员有全场地预约权限，但仍不能突破当天 00:00 锁定、每日最多两次、班次、请假和档期冲突规则。

## 2. 权限基本原则

| 原则 ID | 原则 |
|---|---|
| `AUTH-001` | 所有接口默认拒绝，只有明确列出的权限才允许。 |
| `AUTH-002` | 前端隐藏按钮只改善体验，服务端必须独立校验全部权限。 |
| `AUTH-003` | 主播按绑定的内部主播 ID 识别，不能通过请求参数切换身份。 |
| `AUTH-004` | 运营权限来自有效主播—运营关系，不来自主播姓名或前端缓存。 |
| `AUTH-005` | 客服按场地隔离，首期每个客服只配置一个所属场地。 |
| `AUTH-006` | 管理员拥有全场地数据范围，但不自动拥有突破业务规则的特权。 |
| `AUTH-007` | 每次写操作保存实际操作账号、使用角色、目标对象、修改前后内容和原因。 |
| `AUTH-008` | 同一账号有多个角色时，必须选择当前操作角色；日志记录该角色。 |
| `AUTH-009` | 多角色权限可以合并，但业务限制取最严格且不可绕过的公共规则。 |
| `AUTH-010` | 系统定时任务只能使用专用服务身份，不能模拟普通用户账号。 |
| `AUTH-011` | 五类人员账号统一使用全局唯一登录名和密码；主播登录名固定使用唯一主播编号，编号修改时同步修改登录名；化妆师账号由系统按 `MA0001` 起顺序生成，运营账号由系统按 `OP0001` 起顺序生成，生成后均不可修改，已删除账号的序号不复用。 |
| `AUTH-012` | 新建或重置账号签发临时密码，首次成功验证后必须完成改密，未改密前不得进入业务页面或调用业务接口。 |
| `AUTH-013` | 管理员可以管理全部账号；客服可以进入“账号与角色”，查看管理员账号但只能维护本场地非管理员账号。客服不能编辑、删除或授予管理员账号与管理员角色。 |
| `AUTH-014` | 密码重置必须撤销该账号全部有效会话，并记录操作者、目标账号、场地和原因；日志不得保存明文密码。 |
| `AUTH-015` | 主播编号是主播登录名；管理员或客服修正编号时，人员档案与密码登录身份必须在同一事务同步更新。新编号或登录名冲突时整次修改失败，内部用户 ID、预约和历史记录不变。 |

## 3. 数据范围定义

| 范围代码 | 含义 |
|---|---|
| `SELF` | 仅当前账号绑定的本人业务档案和本人数据 |
| `MANAGED_HOSTS` | 当前由运营负责的主播 |
| `TARGET_DATE_MANAGED_HOSTS` | 目标预约日期存在有效运营关系的主播 |
| `SITE` | 当前客服所属场地内的人员、预约、申请和日志 |
| `ALL_SITES` | 全部场地 |
| `RELATED` | 与本人预约、固定关系或请假直接相关的数据 |
| `SYSTEM` | 仅后台任务可操作 |
| `NONE` | 无权限 |

### 3.1 运营范围的时间规则

- `MANAGED_HOSTS` 用于“负责主播”当前名单，不提供目标日期选择。
- `TARGET_DATE_MANAGED_HOSTS` 只用于预约、改期、取消或固定生效日等未来业务操作的服务端授权，不是主播—运营关系的新字段。
- 创建、改期或取消未来预约：预约目标日期必须存在有效运营关系。
- 发起固定申请：提交时必须是主播当前有效运营。
- 查看负责主播列表和历史预约：主播在查询时必须属于该运营当前负责范围。
- 运营排班查询：按目标日期有效运营关系确定主播范围。
- 关系结束后，运营不能继续打开该主播资料；其过去操作仍保留在审计日志中。

### 3.2 客服场地范围

- 人员主档按人员当前 `site_id` 判断。
- 未来预约按实际预约化妆师场地判断，并要求主播同场地。
- 历史预约按预约保存的场地快照判断。
- 固定、班次和加班申请按提交时场地快照判断。
- 客服不能通过修改请求中的 `site_id` 访问其他场地。

### 3.3 未分配运营

主播没有有效运营关系时：

- 主播本人可以预约、改期和取消。
- 所属场地客服可以代录、改期和取消单次预约。
- 管理员可以操作。
- 任何运营都不能查看或操作该主播。
- 运营端不显示该主播及其预约。
- 不能发起长期固定申请。

## 4. 角色概览

| 角色 | 核心职责 | 默认数据范围 |
|---|---|---|
| 主播 | 为本人预约、管理本人未来预约和查看排班 | `SELF` |

| 客服 | 管理本场地、代录预约、审核申请、导出排班 | `SITE` |
| 管理员 | 全局人员、权限、配置、审批、数据和审计管理 | `ALL_SITES` |
| 系统任务 | 固定生成、自动完成、导出和数据质量任务 | `SYSTEM` |

项目不包含讲师角色。

## 18. 服务端权限校验顺序

每个写接口统一执行：

1. 验证登录会话和账号状态。
2. 确认请求声明的当前角色属于该账号且未撤销。
3. 根据目标业务对象从数据库计算数据范围，不相信前端传入场地或关系。
4. 校验角色动作权限。
5. 校验零点锁定、每日次数、班次、请假、审批状态和冲突等业务规则。
6. 获取必要事务锁并重新校验易变数据。
7. 写入业务数据和审计日志；只有导出等真实异步任务才写外盒事件。

权限失败返回 `403 FORBIDDEN_SCOPE`；业务条件失败返回具体稳定错误码。不得用 `404` 掩盖所有权限错误后又在其他接口泄露对象是否存在。

## 19. 权限测试基线

自动化测试至少覆盖：

1. 主播修改请求中的主播 ID 不能操作他人预约。
2. 运营不能查看或操作未负责、已经结束关系或未分配运营的主播。
3. 客服不能通过修改场地参数访问、审批、导出或代录其他场地数据。
4. 管理员可以跨场地，但仍不能突破当天锁定、每日两次和档期冲突。
5. 化妆师不能创建主播预约，也不能查看其他化妆师完整排班。
6. 主播和化妆师不能操作长期固定关系申请。
7. 只有运营能提交固定申请，只有对应场地客服或管理员能审核。
8. 客服可以为本场地主播代录单次预约，无运营主播同样可代录。
9. 无法匹配运营而留空的主播不会错误授予任何运营权限。
10. 任何角色都不能删除或修改操作日志。
11. 导入确认、角色分配和系统配置只允许管理员。
12. 多角色账号每次操作记录实际选用角色，不能利用角色切换绕过业务限制。
