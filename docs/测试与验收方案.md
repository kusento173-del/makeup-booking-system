# 化妆部预约系统测试与验收方案

> 文档版本：V1.0
> 编制日期：2026-07-20
> 适用范围：开发自测、自动化测试、业务验收、性能测试、安全测试和上线放行

---

## 1. 文档目的

本文档把产品需求、业务规则、权限、数据库约束和页面交互转换为可执行、可复现、可留证据的测试与验收标准。

测试目标不是只证明页面可以点击，而是证明：

1. 预约、固定、班次、请假和审批结果符合业务规则。
2. 多人同时操作时不会产生重复排班或重叠预约。
3. 主播、运营、化妆师、客服和管理员的数据范围不会串场地或越权。
4. 改期、请假、审批和批量任务失败时数据保持一致。
5. 系统在预计规模和并发下仍能响应、恢复和追踪问题。
6. 新系统导出的排班能够替代当前手工整理结果。

---

## 2. 测试依据与冲突处理

测试用例按以下文档执行：

1. 产品需求文档：产品范围和业务目标。
2. 业务规则与状态流转：精确判断顺序、状态和错误码。
3. 角色权限矩阵：角色动作和数据范围。
4. 数据字典与数据库设计：字段、事务、索引和数据库约束。
5. 页面与交互规格：页面路径、字段、提示和交互状态。
6. 现有数据盘点与导入规范：数据清洗、导入和迁移验收。

文档矛盾时不能让测试分别接受两种结果。必须先修正文档、确定唯一预期，再修改实现和测试。

## 3. 测试范围

### 3.1 P0 功能范围

- 登录、账号绑定、角色选择和数据权限。
- 场地、主播、化妆师、运营和负责关系。
- 化妆师首次班次、班次修改、工作日、午休和非工作日。
- 普通预约、第二次提醒、每日最多两次。
- 改期、换化妆师、修改时长和取消。
- 固定新建、变更、取消及审批。
- 主播和化妆师请假。
- 化妆师加班申请及审批。
- 今日、明日、未来七日和历史排班。
- 自动完成、固定滚动生成和任务幂等。
- 小程序内排班和业务结果实时可见。
- Excel 导入、导出和数据质量。
- 操作日志、审批历史和后台任务失败记录。

### 3.2 非功能范围

- 并发一致性。
- API 和页面性能。
- 权限与数据隔离。
- 隐私和敏感数据保护。
- 浏览器及常见手机兼容性。
- 队列、定时任务、备份与恢复。
- 可维护性、自动化覆盖和部署可重复性。

### 3.3 暂不纳入 P0

- 化妆师绩效和奖金计算。
- 直播间预约冲突。
- 未到场状态。
- 第三次或更多预约特批。
- 讲师角色。
- 现有固定主播名单导入。
- 高级经营分析和推荐排班。

## 4. 测试层级与责任

| 层级 | 主要目标 | 推荐执行者 | 自动化要求 |
|---|---|---|---|
| 静态检查 | 类型、格式、依赖和危险代码 | 开发 | 每次提交 |
| 单元测试 | 纯业务规则和计算函数 | 开发 | 核心规则必须 |
| 数据库测试 | 约束、事务、迁移和回滚 | 后端 | 必须 |
| API 集成测试 | 权限、状态和业务闭环 | 后端 | P0 接口必须 |
| 后台任务测试 | 固定生成、导出、重试和自动完成 | 后端 | 必须 |
| 前端组件测试 | 表单、状态和交互分支 | 前端 | 核心组件必须 |
| 端到端测试 | 角色完整流程 | 开发与测试 | 主链路必须 |
| 并发与性能测试 | 抢占、容量和响应时间 | 测试与后端 | 上线前必须 |
| 安全测试 | 认证、越权、输入和隐私 | 测试与后端 | 上线前必须 |
| 业务验收 | 排班可用性和真实业务符合度 | 客服、管理员、业务负责人 | 人工留证 |

任何核心规则不能只依赖人工测试。零点锁定、每日次数、时间冲突、权限和改期原子性必须有自动化测试。

## 5. 测试环境

### 5.1 环境划分

| 环境 | 用途 | 数据 |
|---|---|---|
| 本地开发 | 单元、集成和开发调试 | 自动生成的匿名测试数据 |
| CI | 每次提交自动检查 | 每次运行独立数据库 |
| 测试环境 | 端到端、性能前功能验证 | 脱敏或合成数据 |
| 预发布环境 | 业务验收、迁移演练和发布演练 | 经批准的脱敏生产规模数据 |
| 生产环境 | 正式业务 | 真实数据 |

真实人员 Excel 不得进入源代码仓库、CI 日志或公开测试报告。

### 5.2 固定时钟

测试必须支持注入或冻结系统时间，并统一使用 Asia/Shanghai。至少覆盖：

- 预约日前一天 19:59。
- 预约日前一天 23:59:59。
- 预约日 00:00:00。
- 预约结束前后。
- 跨月、跨年和闰日。

不能依赖测试机器本地时区碰巧正确。

### 5.3 基础测试账号

至少准备：

- 松江主播 A、B，包含一组重名但编号不同的主播。
- 现厂主播 C。
- 无运营主播 D。
- 预约资格暂停主播 E。
- 松江运营 A，负责主播 A、B。
- 现厂运营 B，负责主播 C。
- 松江化妆师 A、B，其中一名未配置班次。
- 现厂化妆师 C。
- 松江客服 A。
- 现厂客服 B。
- 全局管理员 A。
- 同时拥有运营和客服角色的多角色账号。

测试数据必须显式写明场地、关系有效期、班次、请假、固定关系和已有预约，避免用例依赖隐式默认值。

## 6. 测试数据基线

### 6.1 标准班次

- 工作日：周一至周五。
- 上班：08:00。
- 午休：12:00—13:00。
- 下班：18:00。
- 时间粒度：15 分钟。

### 6.2 标准预约日期

设测试当前日期为 D：

- D：今天，只可查看。
- D+1：明天。
- D+7：可预约窗口最后一天。
- D+8：普通预约不可选。

### 6.3 标准预约

- 预约 1：D+1 09:00—09:30。
- 预约 2：D+1 10:00—10:45。
- 相邻不冲突：09:30—10:00。
- 部分重叠：09:15—09:45。
- 跨午休：11:45—12:15。

## 7. 自动化质量门禁

每次合并到主分支前至少通过：

1. TypeScript 类型检查。
2. ESLint。
3. Prettier 检查。
4. 单元测试。
5. 数据库迁移从空库执行成功。
6. API 集成测试。
7. 核心端到端冒烟测试。
8. 依赖安全检查。
9. Git 差异中不存在 Excel、环境密钥、数据库备份和真实人员数据。

### 7.1 微信开发者工具逐页冒烟

每次修改小程序页面、路由、登录态或请求封装后，必须在微信开发者工具中执行：

```powershell
pnpm --filter @makeup/miniapp build
pnpm miniapp:smoke
```

执行前必须满足：

- 微信开发者工具已打开当前 `apps/miniapp` 项目，并在“设置—安全设置”中开启服务端口。
- 工具内已登录与待验收角色一致的测试账号；当前基础用例使用化妆师测试账号。
- 本地 API、PostgreSQL 和 Redis 正常运行。

冒烟命令依次重载首页、我的排班、预约、班次、请假、加班、临时不可排班、固定申请、负责主播、主播详情和未授权兜底页，要求每个页面实例均产生真实视图且运行期间没有小程序异常。命令只读页面，不提交预约、请假、加班、班次或固定申请表单，结束时回到首页并保留工具内登录状态。

出现“路由已进入但视图数为 0”时，判定验收失败。应先清除微信开发者工具编译缓存并按 `Ctrl+B` 强制重新编译，再重复执行；不得仅凭 TypeScript、单元测试、接口响应或 `dist` 中存在页面文件判定微信端可用。

发布候选版本额外通过：

1. 完整端到端回归。
2. 并发和性能测试。
3. 权限与安全回归。
4. 导入及导出核对。
5. 备份恢复演练。
6. 业务验收签字。

### 21.2 数据规模

性能环境至少包含：

- 10,000 名主播。
- 200 名化妆师。
- 300 名运营、客服和管理员账号。
- 3 至 10 个场地。
- 每日 1,500 至 3,000 条预约。
- 至少 12 个月历史预约和操作日志。

### 21.3 负载场景

1. 300 个并发用户持续查询排班和空闲时间 15 分钟。
2. 预约开放高峰中，查询与提交按真实比例混合。
3. 100 个请求同时争抢一个档期。
4. 固定生成、自动完成和普通查询同时运行。
5. 大日期范围历史查询和当天预约同时运行。
6. 单场地与全场地导出同时运行。

测试报告记录应用版本、数据库数据量、机器配置、请求分布、响应分位数、吞吐、错误、数据库锁等待和队列积压。

### 21.4 压力与恢复

逐步增加到 600 并发用户，用于找到拐点而非作为承诺容量。达到保护阈值时系统应限流或延迟非核心任务，不能破坏预约一致性。压力撤除后队列和数据库连接应在可接受时间内恢复。

## 25. 业务验收场景

### 25.1 场景 A：普通预约闭环

1. 主播查看明日无预约。
2. 选择 30 分钟空档并预约。
3. 运营和化妆师看到排班。
4. 主播再创建第二次预约并完成强确认。
5. 第三次被禁止。
6. 主播、运营和化妆师重新查询后看到一致的最新结果。

### 25.2 场景 B：固定与临时变化

1. 运营查看固定可用性。
2. 系统标识固定冲突和未来单次冲突。
3. 运营按推荐开始日期提交。
4. 客服审批通过。
5. 系统生成未来固定预约。
6. 主播临时改到其他时间。
7. 原固定实例已取消，新记录显示单次，长期固定关系不变。

### 25.3 场景 C：化妆师请假

1. 化妆师选择未来三日请假。
2. 系统列出固定和单次受影响预约。
3. 确认后全部取消。
4. 主播和运营重新查询后看到预约已取消和可重新预约状态。
5. 请假后固定关系仍存在。
6. 截止前取消请假后，原固定预约恢复，单次预约保持取消；存在冲突时取消请假失败。

### 25.4 场景 D：客服场地隔离

1. 松江客服查看、代录、审批和导出松江数据。
2. 尝试通过 URL、请求参数和对象 ID 访问现厂。
3. 页面和服务端均拒绝，日志记录安全事件。

### 25.5 场景 E：新旧排班并行

1. 用新系统生成连续七日排班。
2. 与原流程整理表逐日对照。
3. 对预约数量、主播编号、时间、实际化妆师和类型逐项核对。
4. 所有差异有业务原因、迁移原因或缺陷结论。
5. 缺陷关闭后再次核对。

## 26. 缺陷等级与处理

| 等级 | 定义 | 示例 | 上线要求 |
|---|---|---|---|
| S0 | 数据损坏、安全泄露或全系统不可用 | 重叠预约写入、跨场地泄露 | 必须清零 |
| S1 | P0 主流程不可用或结果严重错误 | 无法预约、请假未取消预约 | 必须清零 |
| S2 | 有绕行方案但影响效率或部分用户 | 某次要筛选失效、非核心页面状态异常 | 原则上清零，例外需书面接受 |
| S3 | 轻微展示或文案问题 | 对齐、非关键提示 | 可进入已排期修复清单 |

缺陷单必须包含环境、版本、账号角色、场地、前置数据、步骤、实际结果、期望结果、请求编号和截图或日志证据。

## 30. 文档结论

本系统最重要的质量底线是：任何角色都不能突破日期、次数、班次、请假、场地和时间冲突规则；任何并发、重试或任务失败都不能制造两条重叠有效预约；任何改期和批量取消都必须保留历史并保持事务一致。

测试应从开发第一天与代码同步建设，而不是页面完成后再补。上线放行以自动化证据、并发结果、真实业务排班核对和恢复演练共同决定。
