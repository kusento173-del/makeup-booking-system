# 开发入口

> 适用对象：开发人员、Codex 和代码评审者
>
> 原则：单次任务只加载完成该任务所需的最小上下文。

## 1. 开始任务

1. 查看 `git status`，保护已有未提交改动。
2. 阅读根目录 `AGENTS.md`。
3. 阅读[当前迭代](当前迭代.md)，确认本次任务属于当前阶段。
4. 按[文档索引](README.md)选择与任务直接相关的权威章节。
5. 检查对应代码、测试和最近 Git 提交，不凭聊天记忆猜测现状。
6. 用一句话写清本次结果、范围外事项和验证方式后再实现。

不要默认读取九份正式文档全文。若任务只是排班页面样式，不需要加载全部数据库设计；若任务涉及预约并发，则必须读取业务规则、数据库约束和相关测试要求。

## 2. 系统组成

第一期不是简单的“前端、后端、数据库”三块，而是一个模块化单体系统的七类职责：

| 组成 | 主要职责 |
|---|---|
| 手机端与管理后台 | 主播、运营、化妆师、客服和管理员交互 |
| API 与应用服务 | 用例编排、认证、权限、事务边界 |
| 领域规则 | 预约冲突、次数、固定、班次、请假和状态流转的唯一实现 |
| PostgreSQL | 业务事实、并发约束、历史和审计 |
| Worker 与通知 | 20:00 汇总、一小时前提醒、自动完成、导出和重试 |
| 数据导入与迁移 | Excel 清洗、预检、匹配、导入和核对 |
| 测试、部署与观测 | 自动化测试、CI、容器、日志、监控、备份和回滚 |

代码按业务领域组织，前端、API、数据库和测试共同完成一个业务闭环；不要把任务机械地切成互不校验的三大块。

## 3. 推荐任务粒度

一个合格任务应当：

- 产生一个明确、可验证的用户结果或技术能力。
- 只跨越完成该结果所需的模块。
- 明确包含和不包含什么。
- 包含对应的类型检查、单元测试、集成测试或视觉检查。
- 能形成一次范围清晰的 Git 提交。

示例：

> 实现 D+1 至 D+7 的化妆师可预约时间查询，扣除非工作日、午休、请假、固定格和已有预约，并覆盖边界与数据库集成测试。

不要使用“完成后端”“完成数据库”或“完成预约系统”作为单个任务。

## 4. 实现顺序

每个业务闭环通常按以下顺序推进：

1. 确认业务规则和权限。
2. 定义领域模型与用例边界。
3. 建立数据库迁移、约束和事务。
4. 实现后端 API 与自动化测试。
5. 实现前端交互、状态和错误提示。
6. 接入通知、审计和后台任务（适用时）。
7. 完成端到端、并发或性能验证。

这不是要求在一个巨大提交中完成全部内容。可按可独立验证的能力继续拆分，但数据库、服务端和前端不能长期保留互相矛盾的临时规则。

## 5. 完成标准

- 结果符合对应权威文档。
- 核心规则由服务端实现，必要约束由数据库兜底。
- 正常、失败、越权、边界和并发路径得到与风险匹配的测试。
- 没有真实人员名单、密钥、日志或备份进入 Git。
- 只更新受影响文档，不复制规则到多个位置。
- 检查通过后创建一次 Git 提交，并更新[当前迭代](当前迭代.md)。
