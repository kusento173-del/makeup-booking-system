## 1. 当前目标

在保留微信登录和一次性绑定的前提下，完成主播、运营和化妆师在小程序内的排班查看与业务操作。

第一阶段明确不建设：

- 微信订阅消息、公众号消息或短信。
- 站内消息中心和预约提醒。
- 通知模板、授权记录、发送任务、投递重试及通知后台。

所有业务结果和变化以数据库事实、审计记录和小程序实时查询为准。

微信登录、角色绑定、预约、审计、排班导出及仅供导出使用的通用事务外盒继续保留。删除前实现仍可从 Git 历史查阅，不作为现行需求。

## 4. 已确认决策

| 决策 | 结果 |
|---|---|
| 手机端 | Taro＋React 微信小程序 |
| 首次绑定 | 一次性绑定码；24 小时有效、最多尝试 5 次 |
| 绑定挑战 | 10 分钟有效；过期后小程序自动刷新并只重试一次，不清空表单 |
| 外部消息通知 | 第一阶段不建设 |
| 微信 AppID/AppSecret | 仅用于登录；密钥只保存在本地或部署环境 |
| 讲师角色 | 第一阶段不进入系统 |
| 无法匹配的运营关系 | 留空，不模糊匹配 |
| 历史固定主播名单 | 只作参考，不导入数据库 |
| Excel 导出 | 客服按场地；管理员支持分场地或合并 |

仍待上线前决定：生产云、域名、备案主体和最终部署规模。

- 小程序排班查询、普通预约、取消、改期、化妆师班次、双方请假、加班审批、临时不可排班和固定申请已接入真实 API；首页、排班、班次、请假、加班、临时不可排班和固定申请页已纳入微信开发者工具逐页冒烟。
- 微信开发者工具旧编译缓存可能造成路由存在但页面视图未挂载；小程序改动必须在构建后运行 `pnpm miniapp:smoke`，不能只依赖单元测试和接口检查。
- PostgreSQL 和 Redis 已统一使用 UTC；2026-07-24 已重建本地开发数据卷并通过基础设施检查，业务日期和展示时间继续固定为 `Asia/Shanghai`。
- 本地联调基线包含松江、现厂、无锡三个场地，以及两名主播、两名运营、两名化妆师和两组主播—运营关系；管理员账号已保留，旧登录会话、微信绑定和预约测试数据已清空。
- Taro 的部分开发期间接依赖仍有上游未修复的审计项；生产依赖高危门禁当前通过。
- 仓库尚未配置 GitHub 远程地址，因此只有本地等价 CI 记录。

## 7. 本阶段退出标准

- 小程序不出现订阅消息、通知模板、提醒或发送状态入口。
- 微信登录、会话刷新、首次绑定和角色选择保持可用。
- 请假主体必须由服务端当前身份确定，客户端不能代替他人请假。
- 日期范围、重复请假、撤销截止线和行版本由服务端重新校验。
- 请假创建与受影响预约取消必须原子成功或原子失败。
- 取消尚未开始的请假时，系统原子恢复该请假取消且仍有效的固定预约；单次预约不恢复，固定实例取消后对应日期档期可再次预约。
- 页面具备影响确认、重复提交保护、错误反馈和成功刷新状态。
- 格式、静态检查、类型检查、测试、构建、数据库检查、端到端和安全门禁全部通过。
