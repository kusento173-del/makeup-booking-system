>
> 状态：进行中

## 1. 当前目标

在保留微信登录和一次性绑定的前提下，完成主播、运营和化妆师在小程序内的排班查看与业务操作。

第一阶段明确不建设：

- 微信订阅消息、公众号消息或短信。
- 站内消息中心和预约提醒。
- 通知模板、授权记录、发送任务、投递重试及通知后台。

所有业务结果和变化以数据库事实、审计记录和小程序实时查询为准。

## 3. 本次范围变更

此前开发过的微信通知实现已从现行系统移除：

- API 通知模块及内部接口。
- Worker 通知消费、发送、提醒和每日汇总调度。
- 管理后台通知模板与通知任务页面。
- 小程序订阅授权入口和客户端代码。
- 通知环境变量、数据库模型、约束、检查脚本和数据表。
- 预约、取消、改期和固定流程中的通知外盒写入。

微信登录、角色绑定、预约、审计、排班导出及仅供导出使用的通用事务外盒继续保留。删除前实现仍可从 Git 历史查阅，不作为现行需求。

## 4. 已确认决策

| 决策 | 结果 |
|---|---|
| 手机端 | Taro＋React 微信小程序 |
| 首次绑定 | 一次性绑定码；24 小时有效、最多尝试 5 次 |
| 外部消息通知 | 第一阶段不建设 |
| 微信 AppID/AppSecret | 仅用于登录；密钥只保存在本地或部署环境 |
| 讲师角色 | 第一阶段不进入系统 |
| 无法匹配的运营关系 | 留空，不模糊匹配 |
| 历史固定主播名单 | 只作参考，不导入数据库 |
| Excel 导出 | 客服按场地；管理员支持分场地或合并 |

仍待上线前决定：生产云、域名、备案主体和最终部署规模。

## 5. 当前技术风险

- 小程序当前仍以登录、刷新会话和首次绑定为主，尚未形成完整业务导航。
- Taro 的部分开发期间接依赖仍有上游未修复的审计项；生产依赖高危门禁当前通过。
- 仓库尚未配置 GitHub 远程地址，因此只有本地等价 CI 记录。

## 7. 本阶段退出标准

- 小程序不出现订阅消息、通知模板、提醒或发送状态入口。
- 微信登录、会话刷新、首次绑定和角色选择保持可用。
- 主播只能操作本人预约，运营只能操作目标日期仍由本人负责的主播。
- 当天 00:00 后客户端不展示普通操作入口，服务端仍做最终拒绝。
- 改期失败时原预约保持有效。
- 取消和改期成功后排班列表立即刷新。
- 路由与组件边界清晰，代码简洁且不重复服务端规则。
- 格式、静态检查、类型检查、测试、构建、数据库检查、端到端和安全门禁全部通过。
