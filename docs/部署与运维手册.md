# 化妆部预约系统部署与运维手册

> 状态：待生产资源确定后执行
>
> 最后更新：2026-07-27
>
> 适用范围：第一期响应式网页、API、Worker、PostgreSQL、Redis 和 HTTPS 网关

> 当前部署不包含微信小程序、Taro、AppID、AppSecret、微信合法域名或绑定码配置；旧渠道要求均由[全网页端架构决策](全网页端架构决策.md)替代。

## 1. 部署边界

生产模板由 `compose.production.yaml`、根目录 `Dockerfile` 和 `deploy/nginx.conf` 组成：

- `api`：唯一业务 API，不向宿主机暴露端口；
- `worker`：固定预约生成、预约自动完成、导出处理和清理；
- `gateway`：管理后台静态文件、HTTPS、反向代理和通用限流；
- `migrate`：只在发布时人工执行一次，不随 API 自动运行；
- `backup`：手动或由外部定时器触发的 PostgreSQL 逻辑备份。

生产数据库和 Redis 应优先使用同地域托管服务。不得把生产数据库、Redis、API 调试端口或 Docker 管理端口直接暴露到公网。

## 2. 上线前必须由负责人确定

以下内容依赖真实外部资源，代码无法代替负责人决定：

1. 中国大陆或境外云厂商、地域和应用服务器规格；
2. 正式域名、备案安排和 TLS 证书；
3. 微信小程序合法业务域名、正式 AppID 和 AppSecret；
4. 托管 PostgreSQL、Redis、备份存储和告警接收人；
5. 首个试点场地、上线窗口、回滚负责人和客服值班安排。

未完成这些项目时，只能进行本地或预发布验收，不能称为已具备正式上线条件。

## 3. 生产配置

复制模板但不要提交真实文件：

```powershell
Copy-Item deploy/production.env.example deploy/production.env
```

`deploy/production.env` 已被 Git 忽略。三个密钥必须分别使用独立的高强度随机值；数据库和 Redis 必须启用 TLS。配置完成后执行：

```powershell
pnpm deploy:check
$env:PRODUCTION_ENV_FILE = 'deploy/production.env'
docker compose -f compose.production.yaml config
```

TLS 目录默认为 `deploy/tls`，只允许包含当前服务器本地的 `fullchain.pem` 和 `privkey.pem`，证书和私钥不得提交 Git。也可通过 `PRODUCTION_TLS_DIR` 指向服务器上的受控目录。

## 4. 首次发布

发布前先确认数据库自动备份已开启，然后依次执行：

```powershell
docker compose -f compose.production.yaml build
docker compose -f compose.production.yaml --profile migration run --rm migrate
docker compose -f compose.production.yaml up -d api worker gateway
docker compose -f compose.production.yaml ps
```

迁移必须在单独步骤成功后才启动新版本。禁止把 `prisma migrate deploy` 放进 API 启动命令，避免多个实例同时迁移。

验证项目：

```powershell
curl.exe -I https://你的域名/
curl.exe https://你的域名/healthz
curl.exe https://你的域名/api/health
docker compose -f compose.production.yaml logs --since 10m api worker gateway
```

随后使用管理员、客服、主播、运营和化妆师正式验收账号各走一遍登录和只读查询，再创建、改期、取消一条专用验收预约。不得使用真实业务预约做破坏性测试。

## 5. 发布与回滚

每次发布遵循同一顺序：

1. 记录当前 Git 提交和镜像摘要；
2. 完成数据库备份并验证备份目录；
3. 构建新镜像并运行迁移；
4. 更新 API 和 Worker，最后更新网关；
5. 检查健康、日志和五角色核心冒烟；
6. 记录上线时间、操作者、迁移版本和结果。

应用回滚使用上一版已验证镜像。数据库迁移默认只前进，不自动执行破坏性回滚；若迁移后应用必须回退，应先判断旧应用是否兼容新结构。无法兼容时停止写入并按已演练的备份恢复流程处理。

## 6. 备份与恢复

托管 PostgreSQL 必须开启每日自动备份、时间点恢复和跨可用区存储。仓库提供的逻辑备份用于第二层验证：

```powershell
docker compose -f compose.production.yaml --profile backup run --rm backup
```

该任务会创建自定义格式备份、立即执行目录校验，并清理 35 天前的本地逻辑备份。还必须由云平台或外部任务把备份复制到加密的异地存储；Docker 命名卷不是异地备份。

至少每月在隔离数据库做一次恢复演练：

1. 新建空数据库；
2. 使用 `pg_restore --no-owner --no-acl` 恢复；
3. 执行 `prisma migrate status`；
4. 对场地、人员、关系、班次、预约、固定规则、审计和会话做行数核对；
5. 启动隔离 API 并验证健康、排班和档期查询；
6. 把耗时、文件大小、行数和异常写入验收记录。

## 7. 监控与告警

生产平台至少采集 API、Worker、Nginx、PostgreSQL 和 Redis 的标准输出、资源指标和健康状态。建议阈值：

| 项目 | 告警条件 |
|---|---|
| 网关 5xx | 5 分钟超过 1% 或连续出现 |
| API 健康 | 连续 2 次失败 |
| API 延迟 | 5 分钟 p95 超过 2 秒 |
| API 内存 | 连续 10 分钟超过容器上限 80% |
| PostgreSQL 连接 | 超过连接上限 80% |
| 数据库磁盘 | 可用空间低于 20% |
| Redis | 不可连接或内存超过上限 80% |
| Worker | 连续两轮任务失败或 5 分钟无运行日志 |
| 备份 | 每日备份失败、大小异常或超过 26 小时无新备份 |
| TLS 证书 | 距离到期不足 30 天 |

告警必须到达至少一名技术负责人和一名业务负责人。只写日志但无人接收，不算完成监控。

## 8. 容量与安全

- 当前 600 并发、1,500 单/日基线已通过；生产初始 API 容器限制为 1.5 CPU、1 GiB，Worker 和网关各 0.5 CPU、256 MiB。
- Nginx 对单 IP 提供 300 请求/秒、突发 600 的保护；认证入口另有 Redis 精细限流。
- API 只在 Docker 内网接收流量，并通过 `TRUST_PROXY=true` 使用网关传入的真实客户端地址；不得把 API 容器端口同时映射到公网。
- Nginx 强制 HTTPS、TLS 1.2/1.3、HSTS、1 MiB 请求体和安全响应头。
- 生产密钥、证书、人员名单、导出和备份不得进入 Git、普通聊天或工单正文。

## 9. 日常检查

每天：

- 检查容器、API 健康、Worker 错误和备份成功记录；
- 检查异常 401、403、409、429 和 5xx 是否突增；
- 检查数据库、Redis、磁盘和证书告警。

每周：

- 抽查固定预约生成、自动完成和导出清理；
- 检查管理员、客服账号及离职人员权限；
- 检查最新依赖和镜像安全公告。

每月：

- 完成一次隔离恢复；
- 复核容量趋势和最慢接口；
- 升级证书、依赖或镜像前先在预发布环境运行全量门禁。
